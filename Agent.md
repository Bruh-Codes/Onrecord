## 1. What this system does

Ghanaian SMEs hold their financial history as MoMo statements, bank statements,
photographed receipts, invoices and handwritten ledgers. Lenders cannot assess
that. This system ingests those records and produces a structured, evidence-linked
financial profile plus an explicit list of what is still missing.

Pipeline: `upload → extract → normalise → analyse → score → close gaps → export`.

Target user: registered Ghanaian small business seeking GHS 20,000–200,000, no
bookkeeper, MoMo-primary. Deploying institution: microfinance institution or bank.

Full spec: [`product-spec.md`](./product-spec.md). System design: [`README.md`](./README.md).

## 3. Hard invariants

These are not preferences. A change that violates any of them is wrong and must be
rejected even if it passes tests. They apply wherever the relevant code lives,
frontend or backend.

### INV-1-Money is integer pesewas

All monetary values are integer pesewas (GHS minor units) end to end-`BIGINT` in
Postgres, `number` (never float arithmetic) or `bigint` in TypeScript. Never a
float or `Decimal` in storage or in an arithmetic path. Formatting to `GH¢` happens
only at the display/export boundary. Any field or parameter holding money is named
with a `_pesewas` (or `Pesewas`) suffix.

### INV-2-Three kinds of value, never mixed

| Kind        | Origin                                                                     | May feed an indicator |
| ----------- | -------------------------------------------------------------------------- | --------------------- |
| `EXTRACTED` | Read from a document. Carries `document_id`, `page`, `bbox`, `confidence`. | Yes                   |
| `DERIVED`   | Computed by a named, versioned formula from `EXTRACTED` values.            | Yes                   |
| `DECLARED`  | Stated by the business owner. Unverified.                                  | **No**                |

Every stored figure carries its kind. Export renders `DECLARED` values in a
visually separate treatment and never sums them into a `DERIVED` total.

### INV-3-The LLM may write labels, never amounts

The gap agent's entire write surface is two tools:

- `categorise_counterparty()`-sets the `category` column on existing
  `transaction` rows.
- `record_answer()`-inserts into `declaration`.

The agent MUST NOT be able to insert a `transaction`, alter `amount_pesewas`,
alter any `indicator`, or alter any `readiness_score`. There is no code path for
this. If you are adding an agent tool, it may only write to `transaction.category`,
`counterparty.kind`, or `declaration`.

Numbers appearing in agent output MUST be substituted from tool return values, not
generated by the model. The eval asserts every numeric token in an agent turn
appears in the preceding tool response.

AI evidence review is a separate, non-authoritative write surface. It may create
an append-only review finding containing a status, risk level, reason, and
evidence references. It MUST NOT alter extracted values, transactions,
indicators, readiness scores, document status, or checklist outcomes. A review
finding can make a document ineligible for scoring until a reviewer resolves it;
it never removes the underlying business insight.

### INV-4-Stages are idempotent and resumable

Every pipeline stage is keyed on `(document_id, stage, input_hash)`. Re-running a
stage supersedes prior output; it never mutates it. `extraction` rows are
append-only with a `superseded_by` pointer. A stage MUST NOT depend on in-memory
state from a previous stage-it reads what it needs from Postgres and writes its
result back. A crash re-runs one stage.

### INV-5-No credit scoring

`readiness_score` measures completeness and internal consistency of the file. It
is NOT a credit score, probability of default, or lending recommendation. Credit
reference bureau activity is licensed by Bank of Ghana; this system is not licensed.

Never emit: a default probability, a risk grade, a "recommended loan amount", or
any field that reads as a lending decision. `AFFORDABILITY_HEADROOM` is the single
borderline output and is always rendered with its "not a lending decision" caption.

### INV-6-Statements must reconcile before entering the ledger

`opening_balance + Σ inflows − Σ (outflows + fees + levies) == closing_balance`.
Tolerance: 0 pesewas for deterministic parsers, ±100 pesewas for vision extraction.
A failing statement is marked `reconciliation_failed` and raises a `gap`. It is
never silently accepted. This gate catches both bad OCR and doctored documents.

### INV-7-Provenance is not optional

Every `transaction` row carries `provenance.extraction_ids`. Every `indicator` row
carries `inputs` naming the transaction IDs or indicator codes it consumed. Any
figure in an export must be traceable to a document page. A code path that creates
a transaction without provenance is a bug.

## 5. Conventions

- **File size / structure**: no file over 500 lines. Break work into components /
  modules rather than dumping everything into one file. Applies everywhere.
- **Readability**: write code that's easy to understand and debug-clear names,
  small functions, obvious control flow. No premature abstraction. Comments only
  when they explain a genuinely non-obvious WHY.
- **Timestamps** stored UTC (`timestamptz`). Display timezone `Africa/Accra`.
  Transaction business date is `occurred_on` (a `date` in Accra local terms).
- **IDs** are UUIDv7, not integers.
- **Enums** are Postgres native enums, mirrored as Python `StrEnum`. Adding a
  value requires a migration.
- **PII**: MSISDNs and account numbers are stored hashed
  (`sha256(msisdn + PEPPER)`) with a `display_suffix` of the last 3 digits. Never
  log document content. Extraction prompts and responses are logged with values
  redacted, structure retained.
- **Errors**: API raises a typed `AppError(code, message, http_status)`. Codes are
  stable strings the frontend switches on.
- **Migrations**: every model change ships with an Alembic revision in the same
  commit. Never edit an applied migration.
- **Tests**: `pytest` on the backend. The `adom_provisions` fixture is the
  regression suite for analytics-if you change a formula, its expected values
  change in the same commit, deliberately.

## 6. Language and market facts the code depends on

- Currency GHS only at MVP. FX rows are flagged `flags.fx = true` and excluded
  from all indicators.
- MoMo providers: `MTN`, `TELECEL`, `AT`, `GHANAPAY`, `GMONEY`, `ZEEPAY`.
- MTN self-service statements cover a maximum of 90 days per request and expire
  24 hours after generation. A 12-month history is 4+ uploads. Period stitching
  and the `missing_period` gap exist because of this. Do not assume a single
  statement covers the analysis window.
- MoMo rows carry an operator fee and an e-levy as separate components. These MUST
  be split from the transfer principal or expenses are overstated.
- GRA e-VAT certified invoices carry a digital signature, QR code, invoice number
  and timestamp. They are a high-trust evidence class and score highest in the
  verifiability pillar.
- Ghana Data Protection Act 2012 (Act 843) applies. Consent to analyse records is
  separate from consent to share a profile with a named lender.

## 7. Security and evidence review

- OpenAI credentials live only on the Railway worker/API environment and are
  never sent to the browser, stored in the database, or written to logs.
- Send the minimum sanitized payload needed for a task. Redact MSISDNs, account
  numbers, document identifiers, and long numeric strings before model calls.
  Do not send raw document bytes unless a separately approved visual review
  stage requires them.
- Use strict structured model output, `store: false`, timeouts, bounded retries,
  and fail-closed review status. A model timeout or malformed response creates a
  `pending` review case; it never silently marks evidence as trusted.
- Every AI finding stores its model, input hash, status, risk level, reason, and
  evidence references. Never store a model-generated amount or balance as a
  financial fact.
- Evidence status is distinct from insight status. `clear` evidence may feed
  readiness scoring; `pending`, `warning`, and `error` evidence remains visible
  in insights but is excluded from lender-readiness scoring until a reviewer
  resolves it. Human reviewers use an authenticated API and every decision is
  audit logged.
- Owners may view their own review findings. Reviewer/admin roles may resolve
  cases. Soft-deleted documents and their review findings must never appear in
  client queries.
- Encrypt documents in transit and at rest, use short-lived signed URLs,
  tenant-scope every query, and apply Ghana Data Protection Act consent and
  deletion requirements.

## 8. Pipeline stages and review states

The implemented processing path is:

`upload → Docling extraction → document classification → deterministic facts →
AI evidence review → recompute → insights + readiness score → human review`

The deterministic stages own dates, amounts, balances, reconciliation,
provenance, and exclusions. The AI evidence stage only explains risk signals
and emits a structured review case. Review states are `pending`, `clear`,
`warning`, `error`, `approved`, and `rejected`; only `clear` or reviewer-
`approved` evidence is eligible for readiness scoring. `warning`/`error` cases
remain visible as insights and expose reasons through the review API.
